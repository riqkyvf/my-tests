# Архитектура и подготовка данных

[← README](../README.md)

## Архитектура

Используется **Page Object Model (POM)**: тест описывает сценарий и ожидаемый
результат, Page Object содержит локаторы страницы и действия пользователя.

```text
.
├── tests/                   # Сценарии, expect/assert и шаги Allure
├── pages/                   # Page Objects
│   ├── register_page.py     # Регистрация
│   ├── login_page.py        # Вход
│   ├── profile_page.py      # Личный профиль и навыки
│   ├── slots_page.py        # Управление своими слотами
│   ├── catalog_page.py      # Каталог и поиск
│   ├── person_page.py       # Публичный профиль и подтверждение брони
│   └── meetings_page.py     # Ближайшие и прошедшие/отменённые встречи
├── components/
│   └── header.py            # Общая шапка: вход, выход, профиль
├── api/
│   └── accounts.py          # HTTP-функции создания и удаления аккаунта
├── helpers/
│   ├── users.py             # Уникальные данные пользователей
│   └── dates.py             # Дата/время по Москве и русское представление даты
├── conftest.py              # Все пользовательские фикстуры и фабрики
├── config.py                # Адрес стенда/API, таймауты и часовой пояс
├── pytest.ini               # Сбор из tests/, подробный вывод -v
├── pyproject.toml           # Ruff: линтер, сортировка импортов, форматтер
├── requirements.txt         # Зависимости Python
├── requirements.md          # Требования PomidorQA
├── coverage_matrix.md       # Матрица покрытия
└── AGENTS.md                # Правила разработки автотестов
```

Ответственность слоёв:

| Слой | Ответственность |
| --- | --- |
| `tests/` | Последовательность действий, проверки бизнес-результата, названия и шаги отчёта |
| `pages/` и `components/` | Локаторы, действия и технические ожидания завершения операций |
| `api/` | Отправка HTTP-запросов через Playwright, возврат APIResponse вызывающему коду |
| `conftest.py` | Подготовка пользователей и состояний, проверки предусловий, очистка ресурсов |
| `helpers/` | Повторяемые вычисления и генерация данных без браузерных действий |

Данные передаются обычными словарями. Например, `user_factory` возвращает `user`,
`context`, `page`, а подготовленный слот — `person`, `slot_id`, `slot_date`,
`slot_time`. Отдельного слоя DTO-классов сейчас нет.

## Подготовка данных и авторизация

Все пользовательские фикстуры находятся в корневом `conftest.py`. Каждый тест
получает собственные данные; сценарии не требуют выполнения других тестов перед ними.

| Фикстура | Что подготавливает |
| --- | --- |
| `api_context` | Отдельный APIRequestContext; освобождает его через `dispose()` |
| `created_account` | Уникальный аккаунт через API; после теста удаляет его той же API-сессией |
| `user_factory` | Нужное число участников в отдельных BrowserContext; возвращает данные и страницу каждого |
| `logged_in_page` | Копирует сессионные cookies `created_account` в браузер и проверяет авторизованное состояние |
| `registration_user` | Только генерирует данные: аккаунт создаёт UI-тест; после него фикстура удаляет аккаунт, если появилась сессия |
| `available_person_factory` | Участника с заданными навыками, необязательными данными профиля и одним свободным будущим слотом |
| `booked_slot_factory` / `booked_slot` | Двух участников, слот и бронирование через UI, без перехода в раздел встреч |
| `booked_meeting_factory` / `booked_meeting` | Дополнительно ID встречи гостя и проверку booked у ведущего |
| Специализированные фикстуры | Пользователей для поиска, опубликованный профиль, несколько слотов, участников гонки и встречи для проверки границы отмены |

Аккаунты создаются через `POST /api/pomidorqa/test/accounts`, удаляются через
`DELETE` того же endpoint. Удаляется аккаунт **текущей API-сессии**; связанные
тестовые данные очищаются вместе с ним. Проверяются HTTP-статусы создания и удаления.

`user_factory` отправляет запрос через `context.request`: API и браузерный контекст
используют общие cookies, поэтому созданный участник уже авторизован в своей странице.
У каждого участника свой контекст — сессии ведущего и гостей изолированы.

`created_account` использует отдельную API-сессию. Поэтому выход через UI не мешает
удалить аккаунт в teardown. В тестах самого входа/регистрации действия выполняются
через форму; остальные сценарии используют готовую авторизацию.

Профиль, навыки, слоты и бронирования подготавливаются существующими UI-методами.
Тестовый API аккаунтов не является API управления слотами или встречами. HTTP-запросы
проекта выполняет Playwright APIRequestContext; отдельная библиотека `requests` не используется.

Очистка выполняется после `yield` в `finally`, в том числе при падении проверки.
Ошибки удаления не подавляются. Контексты от `new_context` закрывает pytest-playwright.
При принудительном завершении процесса teardown может не выполниться.

## Даты, ожидания и гонка бронирований

- По умолчанию браузерные контексты используют `Europe/Moscow`; тесты поясов
  явно переопределяют `timezone_id`. Дата компьютера не используется как дата Москвы:
  для этого есть `now_in_moscow()` и `today_in_moscow()`.
- Даты слотов вычисляются относительно текущей даты. Обычная подготовка создаёт
  слот на два дня вперёд; проверки времени явно учитывают часовой пояс профиля.
- UI-результаты проверяются через повторяющиеся `expect`, без фиксированных задержек.
  Сохранение через Next.js Server Actions при необходимости ждёт соответствующего
  POST-ответа; успешным может быть и перенаправление HTTP 303.
- В `ProfilePage` сохранение, добавление и удаление навыка используют приватный
  `_expect_form_response()`. Он ждёт POST к странице профиля; результат изменения
  проверяет вызывающий тест или фикстура подготовки.
- В `SlotsPage` метод `create_slot()` отправляет форму и ждёт POST-ответ и готовность
  кнопки. Метод `submit_slot()` только заполняет форму и нажимает кнопку: он нужен
  для HTML-валидации, которая блокирует отправку. Получение ответа само по себе
  не доказывает создание слота; появление или отсутствие записи проверяет тест.
- В гонке оба гостя открывают подтверждение одного слота. Фикстура удерживает
  сформированные POST-запросы, затем пропускает оба на настоящий сервер без ожидания
  результата первого. Ответы не подменяются локальным моком.
