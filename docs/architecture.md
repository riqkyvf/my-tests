# Архитектура и подготовка данных

[← README](../README.md)

## Архитектура

Используется **Page Object Model (POM)**: тест описывает сценарий и ожидаемый
результат, Page Object содержит локаторы страницы и действия пользователя.

| Расположение | Ответственность |
| --- | --- |
| `tests/` | Сценарии, проверки результата, названия и шаги Allure |
| `pages/` и `components/` | Локаторы, действия пользователя и ожидания завершения операций |
| `api/accounts.py` | HTTP-запросы создания и удаления аккаунтов через Playwright |
| `conftest.py` | Все пользовательские фикстуры: подготовка данных, проверки предусловий и очистка |
| `helpers/` | Генерация данных и вычисления без браузерных действий |
| `config.py` | Адреса, таймауты и часовой пояс по умолчанию |
| `pytest.ini` и `pyproject.toml` | Настройки pytest и Ruff |

Данные передаются словарями. Например, `user_factory` возвращает `user`,
`context`, `page`, а `available_person_factory` — `person`, `slot_id`, `slot_date`,
`slot_time`.

## Подготовка данных и авторизация

Все пользовательские фикстуры находятся в корневом `conftest.py`. Каждый тест
получает собственные данные; сценарии не требуют выполнения других тестов перед ними.

| Фикстура | Что подготавливает |
| --- | --- |
| `api_context` | Отдельный APIRequestContext; освобождает его через `dispose()` |
| `created_account` | Уникальный аккаунт через API; после теста удаляет его той же API-сессией |
| `user_factory` | Нужное число участников в отдельных BrowserContext; возвращает данные и страницу каждого |
| `logged_in_page` | Копирует сессионные cookies `created_account` в браузер и проверяет авторизованное состояние |
| `registration_user` | Только генерирует данные: аккаунт создаёт UI-тест; после него фикстура удаляет аккаунт, если появилась сессия |
| `available_person_factory` | Участника с заданными навыками, необязательными данными профиля и одним свободным будущим слотом |
| `booked_slot_factory` / `booked_slot` | Двух участников, слот и бронирование через UI, без перехода в раздел встреч |
| `booked_meeting_factory` / `booked_meeting` | Дополнительно ID встречи гостя и проверку booked у ведущего |
| `mixed_meetings` | Две независимые пары с одной ближайшей и одной отменённой встречей у каждой; использует повторную бронь освобождённого слота |
| `meetings_in_both_roles` | Участника с двумя ближайшими встречами в разное время: в одной он ведущий, в другой — гость |
| Специализированные фикстуры | Пользователей для поиска, опубликованный профиль, несколько слотов, участников гонки и встречи для проверки границы отмены |

Аккаунты создаются через `POST /api/pomidorqa/test/accounts`, удаляются через
`DELETE` того же endpoint. Удаляется аккаунт **текущей API-сессии**; связанные
тестовые данные очищаются вместе с ним. Проверяются HTTP-статусы создания и удаления.

`user_factory` отправляет запрос через `context.request`: API и браузерный контекст
используют общие cookies, поэтому созданный участник уже авторизован в своей странице.
У каждого участника свой контекст — сессии ведущего и гостей изолированы.

`created_account` использует отдельную API-сессию, поэтому выход через UI не мешает
удалить аккаунт после теста. Тесты входа и регистрации работают с формами.
В остальных сценариях авторизованный участник получает готовую сессию через
`logged_in_page` или `user_factory`; гостевые проверки выполняются без входа.

`booked_slot_factory` и `booked_meeting_factory` принимают необязательный `guest` —
пользователя, ранее созданного через `user_factory`. Без него создаётся новый гость.
Это позволяет готовить встречи одного участника в разных ролях с сохранением
его браузерной сессии и общей очистки данных.

Профиль, навыки, слоты и бронирования подготавливаются существующими UI-методами:
доступный тестовый API позволяет только создавать и удалять аккаунты.

## Очистка данных и шаги Allure

Удаление выполняется в teardown — завершающей части фикстуры, в том числе при
падении подготовки или самого теста. `created_account` и `user_factory` пытаются
удалить аккаунт, если создание вернуло HTTP 201 или появилась сессионная cookie.
`registration_user` удаляет зарегистрированный через UI аккаунт при наличии сессии.

Ошибки удаления не подавляются. `user_factory` обрабатывает всех подготовленных
участников и затем сообщает о накопленных ошибках. API-контекст освобождается
через `dispose()`, браузерные контексты от `new_context` закрывает pytest-playwright.
Принудительное завершение процесса может прервать очистку.

Смысловые блоки подготовки и очистки обёрнуты в `with allure.step(...)` прямо
в фикстурах и возвращаемых ими фабриках. Вложенные шаги помогают определить,
на каком этапе подготовки участника произошёл сбой.
Пароли и значения cookies в названия шагов не передаются.
Шаги сценария находятся в тестах; методы Page Objects не имеют декораторов Allure.

При сетевой ошибке удаления `delete_account()` убирает из исключения Playwright
журнал `Call log` с HTTP-заголовками, сохраняя тип и основное сообщение ошибки.

## Даты и часовые пояса

Браузерные контексты по умолчанию используют `Europe/Moscow`; тесты часовых поясов
явно передают `timezone_id`. Текущие дату и время по Москве вычисляют
`today_in_moscow()` и `now_in_moscow()` из `helpers/dates.py`.

Даты слотов вычисляются относительно текущей даты. Стандартная подготовка создаёт
слот на два дня вперёд; специализированные сценарии задают собственные дату и время
с учётом часового пояса профиля.

## Ожидания и проверки

Состояние интерфейса проверяется через `expect`, без фиксированных задержек.
Методы Page Objects ожидают завершения действий, а тесты и фикстуры проверяют
результат. Получение HTTP-ответа само по себе не подтверждает изменение данных.

| Метод | Что ожидает |
| --- | --- |
| `LoginPage.login()` | POST-ответ формы входа |
| `ProfilePage.save()`, `add_skill()`, `remove_skill()` | POST-ответ страницы профиля через `_expect_form_response()` |
| `SlotsPage.create_slot()` | POST-ответ страницы слотов и готовность кнопки к следующему действию |
| `SlotsPage.submit_slot()` | Только заполняет и отправляет форму, без ожидания POST; применяется при HTML-валидации, блокирующей запрос |
| `PersonPage.confirm_booking_and_close()` | Успех или ошибку формы; при успехе закрывает диалог и возвращает текст, при отказе выбрасывает исключение |
| `MeetingsPage.cancel_meeting()` | POST-ответ отмены и возвращает его вызывающему коду |

Ожидание ответа устанавливается до клика. Сохранение профиля и слотов использует
Next.js Server Actions; методы действий не привязывают результат к HTTP-статусу.

При проверке двухчасового ограничения отмены тест сначала ожидает отменённую
запись или сообщение `cancel-error` и только затем заново открывает страницу.
Повторное открытие убирает сообщение отказа. После этого проверяются состояния
встречи и слота у участников.

## Гонка бронирований

Два гостя открывают подтверждение одного слота. Фикстура
`confirm_bookings_together` удерживает их POST-запросы, затем отправляет оба
на сервер без ожидания результата первого. Ответы сервера не подменяются.
Для отправки используется `PersonPage.confirm_booking()`, который только нажимает
кнопку подтверждения.

Тест проверяет единственного победителя, ошибку проигравшего, отсутствие у него
встречи, общую бронь у ведущего и победителя и статус `booked` исходного слота.
