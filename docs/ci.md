## Режимы запуска

Workflow [PomidorQA tests](../.github/workflows/tests.yml) запускается автоматически
при push в `main`, а также при открытии, обновлении коммитов или повторном открытии
pull request в `main`. Выполняются Ruff и три smoke-теста: UI-регистрация, вход
и основной сценарий бронирования. Для PR фильтр `branches: [main]` относится к целевой ветке.

При ручном запуске в Actions → PomidorQA tests → Run workflow доступен выбор:

- `smoke` — три сценария, используется по умолчанию;
- `full` — полный набор pytest, сейчас 76 случаев с учётом параметризации.

В обоих режимах сначала проверяются Ruff и форматирование. Тесты выполняются
последовательно в Chromium. Скриншоты, видео и trace автоматически не добавляются.

В CI каждый упавший тест повторяется один раз благодаря `pytest-rerunfailures`
и параметру `--reruns 1`: максимум две попытки. Успешные тесты повторно не запускаются.
Если повтор успешен, CI становится зелёным; повторное падение оставляет его красным.
Allure сохраняет обе попытки для разбора нестабильных тестов.
Обычный локальный запуск pytest выполняется без повторов.

Имя проверки постоянно: **Ruff and Chromium tests**. Оно не зависит от набора.
При push и на PR выполняется `smoke`; выбор `full` доступен при ручном запуске.

Вход и бронирование отмечены `@pytest.mark.smoke`. В регистрации маркер задан
через `pytest.param(..., marks=pytest.mark.smoke)` только для пароля из 8 символов;
вариант с 9 символами остаётся в полном наборе. Маркер зарегистрирован в `pytest.ini`.
Workflow выбирает их через `-m smoke`, без перечисления имён тестовых функций.
Локальный запуск той же группы (без автоматических повторов):

```powershell
.\.venv\Scripts\python.exe -m pytest -m smoke --browser chromium
```

## Работа напрямую в main

Для прямой отправки коммитов владелец репозитория настраивает защиту ветки
отдельно от workflow. Изменение YAML не снимает ограничения GitHub.

1. Откройте **Settings → Branches → правило main → Edit**.
2. Отключите **Require a pull request before merging**.
3. Отключите **Require status checks to pass before merging**.
4. Сохраните правило. Разрешения force push и удаления ветки оставьте выключенными.

Теперь CI проверяет коммит после push. Если проверка упала, коммит остаётся
в `main`; исправление отправляется следующим коммитом. При желании можно продолжать
использовать PR: автоматическая проверка для них тоже сохраняется.
Подробности: [защита веток](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule).

## Проверка после публикации

1. Отправьте изменение в `main`: workflow должен запуститься автоматически.
2. В Actions проверьте запуск с событием `push` и результат **Ruff and Chromium tests**.
3. Для проверки полного набора запустите `full` вручную и изучите итог и артефакты.

Не нужно специально ломать тесты ради проверки настройки. Если CI упал из-за
недоступности стенда, изучите результат до повторного запуска.

## Отчёты и повторный запуск

В разделе Artifacts сохраняются `allure-results` и `allure-report` на семь дней.
Если результаты pytest появились, загрузка выполняется и после падения тестов.
Ошибка генерации HTML не препятствует загрузке исходных результатов.

Нажатие Re-run jobs повторяет запуск на прежнем коммите. Для проверки исправления
в PR отправьте новый коммит: событие обновления PR запустит CI автоматически.
Для новой ручной проверки используйте Run workflow и нужную ветку.

Фикстуры создают и удаляют свои аккаунты. Активный запуск не отменяется при новом
запуске той же ветки, чтобы дать очистке завершиться. Принудительная отмена
или общий таймаут job всё равно могут прервать teardown.
