# GitHub Actions и обязательная проверка PR

[← README](../README.md)

## Режимы запуска

Workflow [PomidorQA tests](../.github/workflows/tests.yml) запускается автоматически
при открытии, обновлении коммитов или повторном открытии pull request в `main`.
На PR выполняются Ruff и два smoke-теста: вход и основной сценарий бронирования.
Фильтр `branches: [main]` относится к целевой ветке PR.

При ручном запуске в Actions → PomidorQA tests → Run workflow доступен выбор:

- `smoke` — два сценария, используется по умолчанию;
- `full` — полный набор pytest, сейчас 74 случая с учётом параметризации.

В обоих режимах сначала проверяются Ruff и форматирование. Тесты выполняются
последовательно в Chromium. Скриншоты, видео и trace автоматически не добавляются.

В CI каждый упавший тест повторяется один раз благодаря `pytest-rerunfailures`
и параметру `--reruns 1`: максимум две попытки. Успешные тесты повторно не запускаются.
Если повтор успешен, CI становится зелёным; повторное падение оставляет его красным.
Allure сохраняет обе попытки для разбора нестабильных тестов.
Обычный локальный запуск pytest выполняется без повторов.

Имя проверки постоянно: **Ruff and Chromium tests**. Оно не зависит от набора.
На PR всегда выполняется `smoke`; выбор `full` доступен при ручном запуске.

## Обязательный зелёный CI перед merge

Workflow сообщает результат проверки, а запрет слияния задаётся настройками GitHub.
Для включения правила нужны права администратора репозитория. Изменение YAML
само по себе не включает защиту ветки.

После публикации workflow и появления проверки с новым именем:

1. Откройте **Settings → Branches → Add classic branch protection rule**.
2. Укажите **Branch name pattern: main**.
3. Включите **Require a pull request before merging**. Для самостоятельной работы
   оставьте **Require approvals** выключенным: второй ревьюер не требуется.
4. Включите **Require status checks to pass before merging** и выберите
   **Ruff and Chromium tests**.
5. Включите **Require branches to be up to date before merging**, чтобы проверять
   PR с учётом актуального состояния `main`.
6. Чтобы правило действовало и на владельца, включите
   **Do not allow bypassing the above settings**.
7. Сохраните правило. Не включайте разрешения force push и удаления ветки.

Если имя проверки ещё не предлагается в настройках, сначала выполните новый
запуск workflow с обновлённым именем job и обновите страницу настройки правила.
Подробности: [защита веток](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule).

## Проверка после публикации

1. Создайте рабочую ветку и PR в `main`: workflow должен запуститься автоматически.
2. Убедитесь, что в PR появился статус **Ruff and Chromium tests**.
3. После сохранения защиты проверьте, что до завершения проверки merge блокируется,
   а после успешного завершения становится доступен при выполнении остальных условий.
4. Запустите `full` вручную из основной ветки и проверьте итог и артефакты.

Не нужно специально ломать тесты ради проверки правила. Если CI упал из-за
недоступности стенда, изучите результат до повторного запуска.

## Отчёты и повторный запуск

В разделе Artifacts сохраняются `allure-results` и `allure-report` на семь дней.
Если результаты pytest появились, загрузка выполняется и после падения тестов.
Ошибка генерации HTML не препятствует загрузке исходных результатов.

Нажатие Re-run jobs повторяет запуск на прежнем коммите. Для проверки исправления
в PR отправьте новый коммит: событие обновления PR запустит CI автоматически.
Для новой ручной проверки используйте Run workflow и нужную ветку.

Фикстуры создают и удаляют свои аккаунты. Активный запуск не отменяется при новом
запуске той же ветки, чтобы дать очистке завершиться. Принудительная отмена
или общий таймаут job всё равно могут прервать teardown.
