# PomidorQA — автотесты на Python

[![CI](https://github.com/riqkyvf/my-tests/actions/workflows/tests.yml/badge.svg)](https://github.com/riqkyvf/my-tests/actions/workflows/tests.yml)

Учебный проект функциональных автотестов для [PomidorQA](https://aiqa.su/pomidorqa) —
сервиса, в котором QA/IT-специалисты находят собеседников по навыкам и бронируют
короткие встречи.

**Стек:** Python · pytest · синхронный Playwright · Allure · Ruff.

Тесты работают с реальным стендом. Поднимать приложение локально не требуется;
для запуска нужен доступ к `https://aiqa.su`. Исходного кода приложения в репозитории нет.

## Что реализовано

- **Page Object Model:** локаторы и действия находятся в `pages/` и `components/`,
  проверки поведения — в тестах.
- **Независимые данные:** аккаунты создаются через тестовый API и удаляются
  фикстурами после теста, в том числе при падении проверок.
- **Изоляция сессий:** каждый участник многопользовательского сценария работает
  в отдельном BrowserContext.
- **Проверка бронирования у обеих сторон:** сверяются общий ID встречи,
  участники, дата и время, а также статус исходного слота.
- **Гонка за один слот:** два гостя отправляют подтверждения без ожидания результата
  первого; проверяются единственный победитель и ошибка проигравшего.
- **Часовые пояса:** проверяется отображение времени в поясе владельца,
  включая переход даты, независимо от пояса браузера зрителя.
- **Отчётность и покрытие:** сценарии оформлены шагами Allure, соответствие
  требованиям описано в [матрице покрытия](coverage_matrix.md).

## Быстрый запуск

Команды выполняются **из корня проекта в PowerShell на Windows**.
Нужны Python 3.14 и интернет для установки зависимостей и браузера.
Проверенное локальное окружение: Python 3.14.2.

```powershell
py -3.14 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m playwright install chromium
.\.venv\Scripts\python.exe -m pytest tests/test_login_page.py::test_login_with_valid_credentials
```

Этот тест создаёт аккаунт через API, выполняет вход через форму и проверяет
имя пользователя в профиле. После теста аккаунт удаляется.
Браузер по умолчанию — Chromium без видимого окна; активировать `.venv` необязательно.

Три основных сценария (UI-регистрация с паролем из 8 символов, вход и бронирование)
отмечены маркером `smoke`:

```powershell
.\.venv\Scripts\python.exe -m pytest -m smoke --browser chromium
```

## Покрытие

В наборе **76 запускаемых случаев** с учётом параметризации для Chromium:
75 UI-случаев и одна техническая API-проверка сессионной cookie.
API также используется для подготовки и очистки данных UI-тестов.

| Область | Основные проверки |
| --- | --- |
| Регистрация и авторизация | Создание профиля, автоматический вход, валидация форм, вход с верными и неверными данными, выход, доступ к защищённым страницам |
| Профиль и навыки | Сохранение и очистка полей, оба типа навыков, дубли и удаление, публикация изменений для другого участника |
| Слоты и часовые пояса | Создание и удаление, запрет прошлого времени, сохранение соседних слотов, отображение в поясе владельца |
| Каталог и публичный профиль | Доступность участников, поиск по «могу помочь», пустая выдача, скрытие забронированных слотов |
| Бронирование и встречи | Выбор конкретного слота, встреча у обеих сторон, запрет собственной брони, конкуренция двух гостей |
| Отмена | Двухчасовое ограничение, отмена ведущим и гостем, освобождение слота и повторная бронь третьим участником |

Основной E2E-сценарий: аккаунты через API → навык и свободный слот через UI →
профиль ведущего из каталога гостя → бронь → одна встреча у обеих сторон →
статус `booked` у исходного слота. UI-регистрация и поиск через строку поиска
проверяются отдельными сценариями.

Полный перечень тестов, соответствие требованиям и непокрытые варианты —
в [coverage_matrix.md](coverage_matrix.md). Количество случаев описывает состав
набора, а не процент покрытия или результат последнего прогона.

## Структура проекта

```text
tests/              Сценарии, проверки и шаги Allure
pages/              Page Objects
components/         Общие компоненты интерфейса
api/                HTTP-запросы через Playwright APIRequestContext
helpers/            Генерация пользователей и работа с датами
conftest.py         Фикстуры, фабрики данных и очистка
config.py           Адреса, таймауты и часовой пояс по умолчанию
pytest.ini          Настройки pytest
pyproject.toml      Настройки Ruff
docs/               Подробности архитектуры и подготовки данных
```

Подробное устройство фикстур, авторизации и ожиданий описано
в [документации по архитектуре](docs/architecture.md).
Python-зависимости зафиксированы в [requirements.txt](requirements.txt).

## Запуск тестов

Весь набор:

```powershell
.\.venv\Scripts\python.exe -m pytest
```

Один файл с видимым браузером:

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_login_page.py --headed
```

Проверка состава набора без выполнения сценариев:

```powershell
.\.venv\Scripts\python.exe -m pytest --collect-only -q
```

Адрес стенда задан в [config.py](config.py). Другие браузеры и параллельный запуск
пока не входят в проверенный базовый прогон.

## Allure-отчёт

Для генерации HTML нужен Node.js с npm/npx; проверенное окружение — Node.js 24.11.1.
Allure Report CLI запускается через `npx` без глобальной установки.

Пример: выполнить тест входа и открыть его отчёт.

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_login_page.py::test_login_with_valid_credentials --alluredir=allure-results --clean-alluredir
npx.cmd --yes allure@3.21.0 awesome allure-results --single-file --output allure-report --group-by feature --report-language ru
Start-Process .\allure-report\index.html
```

Для общего отчёта замените путь к тесту в первой команде на нужные файлы
или уберите его для полного набора. При падении тестов команды генерации
и открытия отчёта тоже можно выполнить.

`allure-results/` содержит исходные результаты, `allure-report/index.html` —
готовый автономный отчёт. `--clean-alluredir` удаляет результаты предыдущего прогона:
сохраняйте их отдельно, если хотите сравнивать запуски.
Скриншоты, видео и trace по умолчанию не включены.

## Проверки качества кода

```powershell
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format --check .
```

Правила линтинга и форматирования находятся в [pyproject.toml](pyproject.toml).
Ruff проверяет код; выполнение браузерных сценариев проверяется запуском pytest.

## CI

Workflow [PomidorQA tests](.github/workflows/tests.yml) использует Ubuntu 24.04,
Python 3.14, Chromium и Node.js 24 для Allure. Успешный ручной smoke-запуск
уже проверен на GitHub; новые режимы ниже нужно проверить после публикации изменений.

| Событие | Проверки |
| --- | --- |
| Push в `main` | Ruff и `smoke` |
| Открытие, обновление или повторное открытие PR в `main` | Ruff и `smoke` |
| Ручной запуск с `suite: smoke` | Ruff, UI-регистрация, вход с проверкой профиля и бронирование у обеих сторон |
| Ручной запуск с `suite: full` | Ruff и полный набор из 76 случаев |

Для ручного запуска откройте [Actions](https://github.com/riqkyvf/my-tests/actions),
выберите **PomidorQA tests** → **Run workflow**, затем ветку и набор `smoke` / `full`.
Выбор набора появится после отправки обновлённого workflow в основную ветку.

В завершённом запуске откройте **Artifacts**, скачайте `allure-report`,
распакуйте архив и откройте `index.html` в браузере.

Артефакты хранятся семь дней. Если pytest создал результаты, они сохраняются
и при падении тестов; HTML генерируется отдельным шагом. В CI каждый упавший тест
повторяется один раз: успешный повтор делает проверку зелёной, повторное падение
оставляет её красной. Обе попытки сохраняются в Allure. Обычный локальный запуск
выполняется без повторов. Если сломалась генерация HTML, исходные `allure-results`
всё равно загружаются для дальнейшего разбора.

Секреты для текущих сценариев не нужны: аккаунты создаются и удаляются фикстурами.
Повторные запуски одного PR или ручные запуски одной ветки ожидают завершения
текущего, чтобы не прерывать очистку данных.

Для работы напрямую в `main` отключите обязательный PR и обязательные статусные
проверки в защите ветки. CI проверяет изменения после push; падение проверки
не отменяет отправленный коммит. [Настройка и порядок проверки](docs/ci.md).

## Ограничения и следующие шаги

- Прошедшие слоты, начавшиеся встречи и точная граница отмены за два часа
  требуют подготовки данных или управления серверным временем.
- HTML-валидация и отсутствие действий в интерфейсе не доказывают серверный
  запрет при прямом HTTP-обходе; внутренний статус `confirmed` напрямую не читается.
- Проверка фактической длительности слота в 25 минут исключена из текущего scope
  автоматизации; требование остаётся частью MVP.
- Смешанные списки своих и чужих встреч и полный список часовых поясов
  проверяются отдельными тестами. Границы остальных проверок — в матрице покрытия.
