# PomidorQA — автотесты на Python

Учебный проект функциональных автотестов для [PomidorQA](https://aiqa.su/pomidorqa)
на **Python, pytest и синхронном Playwright**. Результаты оформляются в Allure.

PomidorQA помогает QA/IT-специалистам находить собеседников для коротких звонков:
участник заполняет профиль, добавляет навыки и свободные слоты, другой участник
находит его в каталоге и бронирует встречу.

Тесты работают с реальным стендом `https://aiqa.su/pomidorqa`. Исходного кода
приложения в этом проекте нет; поднимать само приложение локально не требуется.

с учётом параметризации при стандартном запуске в Chromium.

В набор входят:

- **73 UI-случая:** позитивные и негативные функциональные проверки регистрации,
  авторизации, доступа, профиля, навыков, слотов, каталога, бронирования и отмены.
- **Многопользовательские E2E-сценарии внутри UI-набора:** бронирование, встреча
  у обеих сторон, отмена с повторной бронью и гонка за один слот.
- **1 техническая API-проверка:** наличие сессионной cookie после создания
  тестового аккаунта. API также используется для подготовки и очистки UI-тестов.

Основной E2E-сценарий: аккаунты через API → навык и свободный слот через UI →
карточка ведущего в каталоге гостя → подтверждение брони → одна и та же встреча
у обеих сторон → статус `booked` у слота. Регистрация через форму, редактирование
профиля и ввод поискового запроса покрыты отдельными сценариями.

UI-проверки и E2E здесь пересекаются: это не дополнительные наборы сверх 74 случаев.

или подтверждением успешного последнего прогона.

## Архитектура

Используется **Page Object Model (POM)**: тест описывает сценарий и ожидаемый
результат, Page Object содержит локаторы страницы и действия пользователя.

```text
.
├── tests/                   # Сценарии, expect/assert и шаги Allure
├── pages/                   # Page Objects
│   ├── register_page.py     # Регистрация
│   ├── login_page.py        # Вход
│   ├── profile_page.py      # Личный профиль и навыки
│   ├── slots_page.py        # Управление своими слотами
│   ├── catalog_page.py      # Каталог и поиск
│   ├── person_page.py       # Публичный профиль и подтверждение брони
│   └── meetings_page.py     # Ближайшие и прошедшие/отменённые встречи
├── components/
│   └── header.py            # Общая шапка: вход, выход, профиль
├── api/
│   └── accounts.py          # HTTP-функции создания и удаления аккаунта
├── helpers/
│   ├── users.py             # Уникальные данные пользователей
│   └── dates.py             # Дата/время по Москве и русское представление даты
├── conftest.py              # Все пользовательские фикстуры и фабрики
├── config.py                # Адрес стенда/API, таймауты и часовой пояс
├── pytest.ini               # Сбор из tests/, подробный вывод -v
├── pyproject.toml           # Ruff: линтер, сортировка импортов, форматтер
├── requirements.txt         # Зависимости Python
├── requirements.md          # Требования PomidorQA
├── coverage_matrix.md       # Матрица покрытия
└── AGENTS.md                # Правила разработки автотестов
```

Ответственность слоёв:

| Слой | Ответственность |
| --- | --- |
| `tests/` | Последовательность действий, проверки бизнес-результата, названия и шаги отчёта |
| `pages/` и `components/` | Локаторы, действия и технические ожидания завершения операций |
| `api/` | Отправка HTTP-запросов через Playwright, возврат APIResponse вызывающему коду |
| `conftest.py` | Подготовка пользователей и состояний, проверки предусловий, очистка ресурсов |
| `helpers/` | Повторяемые вычисления и генерация данных без браузерных действий |

Данные передаются обычными словарями. Например, `user_factory` возвращает `user`,
`context`, `page`, а подготовленный слот — `person`, `slot_id`, `slot_date`,
`slot_time`. Отдельного слоя DTO-классов сейчас нет.

## Подготовка данных и авторизация

Все пользовательские фикстуры находятся в корневом `conftest.py`. Каждый тест
получает собственные данные; сценарии не требуют выполнения других тестов перед ними.

| Фикстура | Что подготавливает |
| --- | --- |
| `api_context` | Отдельный APIRequestContext; освобождает его через `dispose()` |
| `created_account` | Уникальный аккаунт через API; после теста удаляет его той же API-сессией |
| `user_factory` | Нужное число участников в отдельных BrowserContext; возвращает данные и страницу каждого |
| `logged_in_page` | Копирует сессионные cookies `created_account` в браузер и проверяет авторизованное состояние |
| `registration_user` | Только генерирует данные: аккаунт создаёт UI-тест; после него фикстура удаляет аккаунт, если появилась сессия |
| `available_person_factory` | Участника с заданными навыками, необязательными данными профиля и одним свободным будущим слотом |
| `booked_meeting_factory` / `booked_meeting` | Двух участников, слот и настоящее бронирование через UI |
| Специализированные фикстуры | Пользователей для поиска, опубликованный профиль, несколько слотов, участников гонки и встречи для проверки границы отмены |

Аккаунты создаются через `POST /api/pomidorqa/test/accounts`, удаляются через
`DELETE` того же endpoint. Удаляется аккаунт **текущей API-сессии**; связанные
тестовые данные очищаются вместе с ним. Проверяются HTTP-статусы создания и удаления.

`user_factory` отправляет запрос через `context.request`: API и браузерный контекст
используют общие cookies, поэтому созданный участник уже авторизован в своей странице.
У каждого участника свой контекст — сессии ведущего и гостей изолированы.

`created_account` использует отдельную API-сессию. Поэтому выход через UI не мешает
удалить аккаунт в teardown. В тестах самого входа/регистрации действия выполняются
через форму; остальные сценарии используют готовую авторизацию.

Профиль, навыки, слоты и бронирования подготавливаются существующими UI-методами.
Тестовый API аккаунтов не является API управления слотами или встречами. HTTP-запросы
проекта выполняет Playwright APIRequestContext; отдельная библиотека `requests` не используется.

Очистка выполняется после `yield` в `finally`, в том числе при падении проверки.
Ошибки удаления не подавляются. Контексты от `new_context` закрывает pytest-playwright.
При принудительном завершении процесса teardown может не выполниться.

## Даты, ожидания и гонка бронирований

- По умолчанию браузерные контексты используют `Europe/Moscow`; тесты поясов
  явно переопределяют `timezone_id`. Дата компьютера не используется как дата Москвы:
  для этого есть `now_in_moscow()` и `today_in_moscow()`.
- Даты слотов вычисляются относительно текущей даты. Обычная подготовка создаёт
  слот на два дня вперёд; проверки времени явно учитывают часовой пояс профиля.
- UI-результаты проверяются через повторяющиеся `expect`, без фиксированных задержек.
  Сохранение через Next.js Server Actions при необходимости ждёт соответствующего
  POST-ответа; успешным может быть и перенаправление HTTP 303.
- Для HTML-валидации, блокирующей отправку, серверного ответа не ожидают.
- В гонке оба гостя открывают подтверждение одного слота. Фикстура удерживает
  сформированные POST-запросы, затем пропускает оба на настоящий сервер без ожидания
  результата первого. Ответы не подменяются локальным моком.

## Установка

Команды ниже предназначены для **PowerShell на Windows** и выполняются из корня проекта.
Нужны Python 3.14, доступ к стенду и интернет для установки пакетов и браузера.
Для Allure-отчёта дополнительно нужен Node.js с npm/npx.

```powershell
py -3.14 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m playwright install chromium
```

Активировать виртуальное окружение необязательно: команды явно используют его Python.
Тесты по умолчанию выполняются в Chromium без видимого окна браузера.

## Запуск тестов

Весь набор:

```powershell
.\.venv\Scripts\python.exe -m pytest
```

Один файл или конкретная функция:

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_login_page.py
.\.venv\Scripts\python.exe -m pytest tests/test_login_page.py::test_login_with_valid_credentials
```

Конкретный параметризованный случай и запуск с видимым браузером:

```powershell
.\.venv\Scripts\python.exe -m pytest "tests/test_auth_session.py::test_anonymous_guest_cannot_open_protected_page[profile-chromium]"
.\.venv\Scripts\python.exe -m pytest tests/test_login_page.py --headed
```

Параметр `--debug` относится к отладке самого pytest и создаёт `pytestdebug.log`.
Для обычного запуска он не нужен; для видимого окна используй `--headed`.

Адрес стенда и настройки находятся в [config.py](config.py). Сейчас `BASE_URL`
задан в коде; настройка через переменную окружения отдельно не реализована.
Другие браузеры и параллельный запуск не входят в текущий проверенный базовый прогон.

## Проверки качества кода: Ruff

Ruff устанавливается вместе с зависимостями из `requirements.txt`. Настройки
находятся в `pyproject.toml`: Python 3.14, строки до 100 символов там, где их
может перенести форматтер, отступы по четыре пробела, двойные кавычки и окончания LF.

Проверить код без изменения файлов:

```powershell
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format --check .
```

Первая команда проверяет код и порядок импортов, вторая — оформление.
Обе возвращают ненулевой код завершения при нарушениях; их можно использовать в CI.
Автоматически применить доступные безопасные исправления и отформатировать код:

```powershell
.\.venv\Scripts\python.exe -m ruff check . --fix
.\.venv\Scripts\python.exe -m ruff format .
```

Включены правила:

| Группа | Что проверяет |
| --- | --- |
| `E4`, `E7`, `E9` | Базовые ошибки оформления и конструкции Python |
| `F` | Неопределённые/неиспользуемые имена и другие ошибки Pyflakes |
| `I` | Сортировка и группировка импортов |
| `B` | Распространённые ошибки и подозрительные конструкции |
| `PT` | Единый стиль pytest-фикстур, параметризации и проверок |

Не включены правила `ARG`: аргумент-фикстура может запускать подготовку, даже если
его значение не читается в теле теста. Проверка длины `E501` отдельно не включена:
переносы делает форматтер, а длинный текст сообщений/локаторов может оставаться цельным.
Виртуальное окружение, кэши и папки результатов не входят в проверяемый код.

Ruff не выполняет браузерные сценарии и не проверяет соответствие продукта требованиям.
После исправлений запускаются затронутые тесты; чистое форматирование можно проверить
через сбор pytest и сравнение структуры кода без нового полного браузерного прогона.

## Allure-отчёт

Запуск с новым набором результатов и генерация одного HTML-файла:

```powershell
.\.venv\Scripts\python.exe -m pytest --alluredir=allure-results --clean-alluredir
npx.cmd --yes allure@3.21.0 awesome allure-results --single-file --output allure-report --group-by feature --report-language ru
Start-Process .\allure-report\index.html
```

Первая команда выполняет тесты, вторая создаёт отчёт, третья открывает его в браузере.
При падении pytest всё равно выполни команду генерации, чтобы посмотреть причину.
CLI запускается через `npx` без глобальной установки; при первом запуске он скачивается.

- `allure-results/` — исходные результаты, шаги и сведения о фикстурах.
- `allure-report/index.html` — готовый автономный отчёт.
- `@allure.feature` объединяет тесты в функциональные группы.
- `@allure.title` задаёт читаемое название; `with allure.step(...)` — этапы сценария.
- Подготовка, тело теста и завершение отображаются отдельно.

В текущем коде **11 функциональных групп и 178 блоков шагов** на 49 функций.
Параметризованные варианты различаются в названиях/параметрах отчёта.

`--clean-alluredir` начинает новый прогон, удаляя предыдущие результаты в указанной
папке. Если нужно сохранить первую неуспешную попытку и добавить повтор отдельного
теста в тот же отчёт, запускай его с `--alluredir=allure-results` без очистки, затем
снова генерируй HTML. Папки результатов и отчёта исключены через `.gitignore`.
Скриншоты, видео и trace по умолчанию не включены.

## Границы покрытия

Актуальные ограничения и следующие проверки перечислены в
[матрице покрытия](coverage_matrix.md). Сейчас:

- Для прошедших слотов/начавшихся встреч и точной границы отмены за 2:00:00
  не хватает подготовки данных или управления серверным временем. Изменение
  часов браузера не меняет время сервера.
- Серверный запрет удаления чужого слота нельзя доказать доступным UI;
  API удаления слотов в распоряжении проекта нет.
- Внутренний статус `confirmed` напрямую не читается: проверяется результат в UI.
- Изоляция смешанных списков своих/чужих встреч и полный список десяти поясов
  пока покрыты частично.
- Проверка фактической длительности записи в 25 минут исключена из текущего scope
  автоматизации по принятому решению. Само требование остаётся в MVP.
- Нативная HTML-валидация доказывает запрет через форму, но не запрет обхода
  интерфейса прямым HTTP-запросом.

Количество собранных случаев не равно количеству полностью проверенных требований.
Процент code coverage приложения не измеряется.

## Как добавлять и изменять тесты

1. Сверить ожидаемое поведение с `requirements.md` и существующей матрицей.
2. Переиспользовать подходящие фикстуры; новые размещать в `conftest.py`.
3. Локаторы и действия разместить в Page Object или общем компоненте,
   проверки результата и смысловые шаги Allure — в тесте.
4. Использовать свои уникальные данные и обеспечить их очистку. Для UI предпочитать
   семантические локаторы и `expect`, а для HTTP-статусов/обычных данных — `assert`.
5. После локального изменения запускать изменённые и непосредственно связанные
   сценарии. Полный прогон выполнять при широких изменениях или отдельной проверке набора.
6. Обновить матрицу и, если изменился состав набора, число случаев в README.
   Сбор `--collect-only` проверяет состав, но не успешность сценариев.

При разборе падения сохранять исходный результат. Успешный повтор одного теста
не превращает первый полный прогон в полностью успешный.

## CI

CI пока **не подключён**. Следующий этап — GitHub Actions: установка окружения,
запуск тестов и сохранение Allure-отчёта как артефакта, в том числе при падении тестов.
Триггеры, команды и порядок работы с CI будут добавлены сюда после реализации workflow.
