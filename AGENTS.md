# Инструкции для агента: PomidorQA autotests

## Назначение и формат помощи

Это учебный проект автотестов PomidorQA на Python, pytest и синхронном Playwright.
Общайся на русском. Объясняй новые конструкции простыми словами, по шагам.
Если пользователь просит объяснить или проверить код, помогай разобраться и не
переписывай его без необходимости. Если просит реализовать — выполняй изменение
и объясняй результат. Не добавляй сложные абстракции без конкретной пользы.
Сейчас приоритет — happy path; негативные сценарии добавляй по отдельной задаче.

## Источники правил

- Перед написанием или изменением тестов применяй навык `playwright-best-practices`
  и читай относящиеся к задаче разделы. Примеры TypeScript адаптируй к Python,
  `playwright.sync_api` и pytest; не переносись на Playwright Test для Node.js.
- Если навык недоступен, сообщи об этом; не утверждай, что прочитал его.
- `requirements.md` — требования к продукту. Перед выбором ожидаемого результата
  читай соответствующий раздел. `requirements.txt` — зависимости Python.
- Проверяй текущее состояние кода: этот файл описывает договорённости и устройство
  проекта, но не заменяет чтение реализации. При расхождении сайта с требованиями
  сообщай о нём, не подгоняй проверки под ошибочное поведение.

## Структура и ответственность

- `tests/test_*.py` — сценарии и проверки ожидаемого поведения.
- `conftest.py` — все пользовательские pytest-фикстуры, включая фабрики, подготовку
  данных и создание Page Objects. Не объявляй фикстуры в файлах тестов.
- `pages/` — Page Objects: локаторы страниц и действия пользователя.
- `components/` — повторяющиеся компоненты интерфейса, например шапка.
- `api/` — функции HTTP-запросов через Playwright APIRequestContext.
- `helpers/` — генерация данных и небольшие вспомогательные функции.
- `config.py` — адреса и настройки; `pytest.ini` — настройки pytest.
- `pyproject.toml` — настройки Ruff; не дублируй их в отдельных конфигурациях.

Перед добавлением кода найди и переиспользуй существующие методы и фикстуры.
Действия и локаторы размещай в Page Objects; проверки результата сценария —
в тестах. Проверки успешной подготовки и очистки данных допустимы в фикстурах.
Не создавай скрытые зависимости между тестами и порядком их запуска.

## API, авторизация и тестовые данные

Используй Playwright для HTTP и UI; библиотеку `requests` не добавляй без задачи.
Базовый адрес и адрес API бери из `config.py`.

- `api_context` создаёт отдельный APIRequestContext и освобождает его через
  `dispose()` в teardown.
- `created_account` создаёт аккаунт через отдельный API-контекст и удаляет его
  после теста. Возвращает данные пользователя и его API-контекст.
- `user_factory` создаёт независимых пользователей через `new_context()` и
  `context.request`; возвращает словарь с `user`, `context`, `page`.
  API-запросы такого контекста делят cookies с его браузерными страницами.
  Дополнительные настройки контекста можно передать в фабрику именованными
  аргументами, например `user_factory("viewer", timezone_id="Asia/Vladivostok")`.
- `registration_user` генерирует уникальные данные без создания аккаунта через API.
  Тест регистрирует пользователя через `RegisterPage`; teardown удаляет аккаунт
  через `page.context.request`, если после UI-регистрации появилась сессия.
- `logged_in_page` копирует сессионные cookies из API-контекста
  `created_account` в контекст стандартной `page`, открывает каталог и проверяет
  авторизованную шапку. Форма входа проверяется отдельными тестами авторизации.
- `available_person_factory` переиспользует `user_factory` и готовит участника
  с заданными навыками и одним свободным будущим слотом. Возвращает `person`,
  `slot_id`, `slot_date`, `slot_time`. Специализированные фикстуры используют её.
- `searchable_people` готовит двух участников со слотами для поиска по навыку.
- `booked_slot_factory` / `booked_slot` создают участников и бронируют слот через UI,
  проверяя сообщение успеха. Они не открывают встречи и слоты после бронирования.
  Используй их, когда ID встречи не нужен, например для каталога и публичного профиля.
- `booked_meeting_factory` / `booked_meeting` дополняют эту подготовку: получают ID
  встречи гостя и проверяют статус booked у ведущего. Нужны сценариям работы со встречей.

Регистрацию и удаление выполняют `create_account` и `delete_account` из
`api/accounts.py` через `/api/pomidorqa/test/accounts`. Удаляется аккаунт текущей
API-сессии; не рассчитывай на удаление произвольного пользователя по ID.
Выход через UI очищает общие cookies браузера и `context.request`, поэтому
учитывай это при организации teardown.

Создавай уникальные данные для каждого теста и отдельный BrowserContext для
каждого участника. Не используй чужие аккаунты и существующие записи сайта как
предусловие. Очищай свои данные даже при падении теста через teardown фикстур.
Не подавляй ошибки очистки. Контексты от pytest-фикстуры `new_context` закрывает
плагин; для ресурсов, созданных вручную, обеспечивай собственное освобождение.

Изменения профиля и слотов могут использовать Next.js Server Actions.
Не придумывай REST endpoints и не копируй изменяемые `next-action` идентификаторы.
Если подходящего API нет, используй существующие UI-методы подготовки данных.

## Локаторы, ожидания и проверки

- Предпочитай `get_by_role`, `get_by_label` и стабильные `get_by_test_id`.
  При необходимости используй существующие `data-slot-id`, `data-person-id`,
  `data-booking-id`, `data-skill-tag`; ограничивай поиск нужной карточкой/секцией.
- Не придумывай локаторы. Проверяй DOM в браузере или используй предоставленную
  разметку. Не маскируй неоднозначность через `.first` или `.nth` без основания.
- Для UI используй повторяющиеся проверки `expect(locator)` и `expect(page)`.
  Для обычных данных и HTTP-статусов допустим Python `assert`.
- Не используй `sleep`, `wait_for_timeout` и увеличение таймаутов как исправление
  гонки. Ожидай конкретное состояние UI или относящийся к действию ответ.
  Подписку `expect_response` устанавливай до действия, вызывающего запрос.
- Повторяющееся подтверждение брони и закрытие окна выполняет
  `PersonPage.confirm_booking_and_close()`. Метод ждёт статус успеха, закрывает
  окно и возвращает текст сообщения; ожидаемый текст и данные встречи проверяет
  вызывающий тест или фикстура подготовки.
- Открывай профиль из карточки через `CatalogPage.open_person(card)`: метод читает
  href, нажимает на карточку и ждёт целевой URL. Проверки данных профиля остаются в тесте.
- После сохранения при проверке персистентности дождись завершения сохранения,
  перезагрузи страницу и проверь сохранённое значение.
- Обычные браузерные контексты используют `DEFAULT_PROFILE_TIMEZONE`
  (`Europe/Moscow`); тесты часовых поясов явно переопределяют `timezone_id`.
  Текущее время и дату по Москве получай через `now_in_moscow()` и
  `today_in_moscow()` из `helpers/dates.py`, не через локальную дату компьютера.
- `SlotsPage.submit_slot()` заполняет и отправляет форму без ожидания POST:
  используй его при HTML-валидации, которая блокирует отправку в браузере.
  `create_slot()` ждёт POST-ответ и готовность кнопки к следующему действию;
  появление или отсутствие слота проверяет тест. Серверный отказ тоже может
  вернуть POST-ответ, поэтому метод сам по себе не доказывает создание слота.
- В `ProfilePage` и `SlotsPage` приватный `_expect_form_response()` создаёт
  ожидание POST к соответствующей странице. Подписку устанавливай до клика.
  HTTP-статус и результат изменения данных — разные условия; результаты этих
  UI-сценариев проверяются в тестах, без привязки действий POM к статусам Next.js.
- Даты слотов задавай в будущем; учитывай часовой пояс владельца профиля из
  требований. Не привязывай тест к фиксированной календарной дате.
- Проверяй результат на конкретной своей записи. Параметризуй одинаковые
  сценарии с разными данными, когда это сохраняет понятность теста.

Проверка фактической длительности слота (25 минут, R7.4 в матрице) исключена
из текущего scope автотестов по решению пользователя: нет доступа к API/данным
для проверки длительности созданной записи. Не добавляй вместо неё проверку
текста «25 минут» и не возвращай её в план без новой задачи. Само требование
остаётся частью MVP.

## Ruff: линтинг и форматирование

Ruff зафиксирован в `requirements.txt`; конфигурация — в `pyproject.toml`.
Используем Python 3.14, длину строки 100, отступы 4 пробела, двойные кавычки и LF.
Правила: `E4`, `E7`, `E9`, `F`, `I`, `B`, `PT`. Не включай `ALL` без разбора пользы
и совместимости правил с pytest/Playwright. `ARG` не включён: неиспользуемый
аргумент-фикстура может быть необходим для подготовки. `E501` не включён:
переносы выполняет форматтер без принудительного разрыва длинных текстов.

После правок Python-кода проверяй:

```powershell
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format --check .
```

Для исправления используй `ruff check . --fix` и `ruff format .` через Python
виртуального окружения. Не применяй `--unsafe-fixes` без отдельного разбора.
Не скрывай замечания общими ignore/noqa, если можно исправить причину.
Проверки Ruff не заменяют запуск затронутых тестов. При чистом форматировании
и сортировке импортов достаточно сравнения AST/импортов и `pytest --collect-only`;
полный браузерный прогон ради пробелов и переносов не требуется. При изменении
действий или проверок запускать соответствующие сценарии обязательно.

## Allure: единый стиль отчётов

Python-зависимость `allure-pytest` фиксируется в `requirements.txt`; отдельный
Allure Report CLI создаёт HTML-отчёт из результатов плагина. Для CLI используем
Node.js и `npx.cmd --yes allure@3.21.0`, без глобальной установки.

- Эталон оформления — `test_login_with_valid_credentials` в `tests/test_login_page.py`.
- Добавляй `@allure.feature("Название функциональности")` для группировки и
  `@allure.title("Понятное ожидаемое поведение")` для названия теста на русском.
- Оформляй сценарий смысловыми блоками `with allure.step("Действие или проверка")`.
  Шаги должны объяснять пользовательский сценарий; не выделяй каждый fill/click.
- Проверки результата оставляй в соответствующем шаге теста. Не переноси их
  в Page Objects ради отчёта и не подавляй исключения для получения зелёного статуса.
- Подготовку и очистку оставляй в фикстурах `conftest.py`: Allure отображает их отдельно.
- Не дублируй одинаковые шаги в тесте и Page Object. На текущем этапе используем
  контекстные шаги в тестах; декораторы методов добавляй только по отдельной задаче.
- Не включай пароли и сессионные cookies в названия шагов, параметры или вложения.
- Все тесты оформлены в едином стиле Allure. Новые и изменяемые сценарии тоже
  должны иметь feature, понятный title и смысловые шаги. Не добавляй скриншоты,
  видео и trace автоматически: диагностика пока отложена.

Из корня Python-проекта запустить только эталонный тест с новым набором результатов:

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_login_page.py::test_login_with_valid_credentials --alluredir=allure-results --clean-alluredir
npx.cmd --yes allure@3.21.0 awesome allure-results --single-file --output allure-report --group-by feature --report-language ru
```

Полный прогон с новым общим отчётом (только при изменениях всего набора или по запросу):

```powershell
.\.venv\Scripts\python.exe -m pytest --alluredir=allure-results --clean-alluredir
npx.cmd --yes allure@3.21.0 awesome allure-results --single-file --output allure-report --group-by feature --report-language ru
```

Отчёт находится в `allure-report/index.html`; его можно открыть в браузере.
`allure-results/` содержит исходные результаты, `allure-report/` — готовый отчёт.
Не смешивай результаты разных прогонов; `--clean-alluredir` предназначен для
начала нового локального прогона. Для общего отчёта нескольких тестов передавай
их одним запуском pytest. Обычный запуск без `--alluredir` остаётся доступным.

## Запуск и отчёт о результате

Запускай команды из корня этого Python-проекта в PowerShell:

```powershell
.\.venv\Scripts\python.exe -m pytest --collect-only -q
.\.venv\Scripts\python.exe -m pytest tests/test_catalog_page.py
.\.venv\Scripts\python.exe -m pytest tests/test_catalog_page.py::test_catalog_search_finds_people_by_can_help_skill
.\.venv\Scripts\python.exe -m pytest tests/test_catalog_page.py --headed --tracing=retain-on-failure --screenshot=only-on-failure
```

Не запускай весь набор после каждого изменения: выбирай изменённые тесты и
сценарии, непосредственно использующие изменённый код. Полный прогон нужен
при изменениях с широким влиянием или по отдельному запросу пользователя.

После изменения кода запускай затронутые тесты; при изменении общих фикстур —
также использующие их сценарии. При падении изучай traceback и trace, исправляй
причину. Если запуск недоступен, прямо сообщи об ограничении.
В итоговом сообщении указывай, что изменено и какие проверки фактически прошли.
Сборка тестов через `--collect-only` не означает успешный прогон сценариев.
При изменении только документации запуск браузерных тестов не требуется.
